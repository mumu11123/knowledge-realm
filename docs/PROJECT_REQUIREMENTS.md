# 项目任务：开发移动端互动式408考研学习平台「知境」

你现在是一名经验丰富的全栈软件工程师，同时具备Java后端架构、Vue前端开发、数据库设计和软件工程实践经验。

请帮助我从零开始开发一个真实可运行、结构清晰、方便维护和扩展的个人开源项目。

项目名称：知境（Knowledge Realm）

项目定位：面向计算机考研408的移动端互动式学习平台。

这个项目未来计划升级为基于Java + Spring AI的AI Agent学习系统，因此请重视代码结构、模块设计、接口规范和可扩展性。

但现阶段不要过度设计，也不要提前集成AI大模型。

## 一、项目核心理念

传统学习通常需要用户阅读大量文字，而本项目希望将知识点融入生活场景和互动剧情。

用户不再只是被动阅读，而是：

1. 选择学习科目。
2. 选择章节或知识点。
3. 进入一个生活化互动故事。
4. 阅读剧情并面对问题。
5. 在多个选项中作出选择。
6. 根据选择显示对应剧情反馈。
7. 逐项解释所有选项的含义及正确或错误的原因。
8. 展示严谨的专业知识总结。
9. 解锁知识卡片。
10. 记录学习进度并支持以后复习。

产品需要兼顾趣味性、知识准确性和实际学习效果。

不能为了故事合理而编造错误知识。

故事与知识必须解耦。

采用前后端分离的单仓库结构。

建议如下：

knowledge-realm/
├── frontend/

├── docs/
├── scripts/
├── docker-compose.yml
├── .gitignore
├── .env.example

其中：

frontend：移动端Vue项目。

backend：Spring Boot后端项目。

scripts：初始化或辅助开发脚本。

AGENTS.md：项目开发规范，方便后续Codex继续开发。

后端使用清晰的分层架构，例如：

controller

mapper

dto
vo
config
exception
common

避免将业务逻辑全部写进Controller。

## 四、移动端UI要求

采用Mobile First设计。

优先适配320px～430px宽度的手机屏幕，同时兼容桌面浏览器。

整体风格：

- 温柔、轻盈、现代。
- 具有轻量游戏化氛围。
- 蓝紫色系为主要视觉方向。
- 大圆角卡片。
- 适当留白。
- 使用简洁的SVG图形、渐变和CSS动画。
- 不使用大量外部图片。
- 避免页面密密麻麻。
- 不设计成传统考试刷题软件。

页面需要流畅、清晰，并且有良好的触摸交互。

请统一设计系统，包括：
- 页面背景
- 颜色变量
- 字体层级
- 按钮样式
- 卡片样式
- 加载状态
- 错误状态
- 空数据状态
- 页面过渡效果

优先使用SVG、CSS完成简单插画与动态效果。

## 五、必须实现的页面

### 1. 首页

首页展示产品名称「知境」。

副标题：
“在故事里，理解知识。”

展示408四门科目：

- 数据结构：开放。
- 计算机组成原理：即将开放。
- 操作系统：即将开放。
- 计算机网络：即将开放。

暂未开放的科目要保留独立标识和未来扩展入口。

可以增加：
- 继续上次学习
- 今日复习入口
- 学习进度概览

第一版不需要真实排行榜或虚假的学习数据。

### 2. 数据结构知识地图

用户点击数据结构后，进入知识地图。

首先展示章节：

1. 绪论和基本概念。
2. 线性表。
3. 栈、队列和数组。
4. 树与二叉树。
5. 图。
6. 查找。
7. 排序。

章节结构需要支持继续细分。

每个知识点包含：
- ID
- 名称
- 章节
- 简介
- 前置知识点
- 关联知识点
- 内容审核状态
- 学习资源状态

界面应区分：
- 暂无教学内容
- 已开放故事
- 已完成学习
- 待复习

不能把尚未制作的知识点标记为已经掌握。

### 3. 互动剧情页面

这是整个项目最重要的页面。

整体采用类似移动端互动小说的设计。

包含：
- 故事标题
- 场景信息
- 简洁插画或背景
- 剧情文本
- 当前学习进度
- 选项卡片
- 提交选择按钮

剧情不能一次性展示全部。

先显示当前场景和选项。

用户选择后，才能解锁反馈和解析。

支持正确选择与错误选择显示不同的剧情反馈。

第一版只需实现有限分支，不需要复杂的剧情树编辑器。

### 4. 选项解析页面

这是必须重点实现的功能。

用户提交答案后，不只显示对错。

系统必须对所有选项提供以下信息：

- 选项名称
- 对应专业术语
- 通俗含义
- 是否符合当前题目
- 正确或错误的原因
- 容易产生的误区

例如：
A 顺序表
B 单链表
C 栈
D 队列

即使用户选择A，也需要允许用户展开B、C、D的完整解析。

解析必须在服务端保存，而不是前端随意生成。

答案提交前，题目查询接口不能直接返回正确选项标记、完整解析或后续剧情，以免提前泄露答案。

后端负责判断答案是否正确。

提交后返回标准化解析结果。

### 5. 知识卡片页面

每完成一个知识点，可以解锁对应知识卡片。

知识卡至少包含：

- 知识点名称
- 对应章节
- 专业定义
- 通俗解释
- 关键结论
- 常见误区
- 简单示意图（如适用）
- 关联故事

实现卡片翻转交互。

卡片可以收藏和复习。

用户可以通过卡片返回对应故事。

### 6. 我的学习页面

展示：
- 已完成故事
- 已接触知识点
- 已解锁知识卡
- 收藏卡片
- 最近学习记录

第一版暂时不需要注册和登录。

使用浏览器本地存储保存游客的学习进度、卡片收藏和简单复习状态。

请封装学习记录存储逻辑，以便将来迁移到后端账户体系。

不要在没有用户登录的情况下伪造跨设备同步功能。

## 六、数据库设计要求

核心数据至少包含：

subject：科目。

chapter：章节。

knowledge_point：知识点。

story：故事。

story_knowledge：故事与知识点的关联关系。

question：互动问题。

question_option：问题选项与解释。

knowledge_card：知识卡片。

其中：

一个故事可以关联多个知识点。

一个知识点可以关联多个故事。

知识点与故事不能强制一对一绑定。

每个选项必须具有独立解析字段。

故事要支持不同选择对应不同反馈。

需要预留：
- 内容来源
- 教材或考纲版本
- 内容审核状态
- 内容创建时间
- 内容更新时间

使用Flyway创建数据库表结构和初始化数据。

提供必要索引、外键和唯一约束。

不要依赖Hibernate自动建表作为正式数据库版本管理方式。

## 七、知识准确性要求

这是高优先级约束。

1. 知识库与故事库必须分离。
2. 不允许为了故事趣味性而篡改专业定义。
3. 所有时间复杂度结论必须考虑适用条件。
4. 区分生活类比与真实计算机实现。
5. 选项解析必须有明确依据。
6. 正式教学内容需要记录来源。
7. 未审核内容不能被标记为正式发布。
8. 对于无法确认的知识点，不得编造教材页码、官方出处或者考研真题来源。

第一版可以提供少量演示知识内容，但必须在界面中明确标记为演示内容，不能宣称已完成整门课程的考纲覆盖和内容审核。

请建立完整的知识目录基础框架，但只制作约3个完整演示故事。

建议故事主题：

- 顺序表与单链表的区别
- 栈的后进先出
- 队列的先进先出

每个故事必须具有清晰且不含歧义的问题。

尽量将知识融入真实生活场景。

## 八、后端接口

请设计RESTful API。

至少支持：

GET /api/subjects

GET /api/subjects/{id}/chapters

GET /api/chapters/{id}/knowledge-points

GET /api/stories/{id}

POST /api/stories/{id}/answer

GET /api/knowledge-points/{id}

GET /api/knowledge-cards/{id}

可以根据实际业务合理调整接口结构。

需要：
- 统一响应格式
- 参数校验
- 全局异常处理
- 合理的HTTP状态码
- 清晰的DTO和VO
- API文档

不要将数据库Entity直接暴露给前端。

回答题目的接口需要验证故事、题目和选项的有效性。

避免客户端直接传入正确答案进行判分。
